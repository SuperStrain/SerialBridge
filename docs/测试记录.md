## 4. 需人工验证的项目（无对应硬件/环境，未标记为已验证）

以下需求点无法在本机自动化完成，请按步骤人工验证：

1. **真实设备双向通信**：将串口设备（如单片机）接入 COM7，并把设备的 TX/RX 短接做环回：
   - 打开 SerialBridge → 启动映射 → 用任意 TCP 工具（如 `telnet <IP> 9001`）发送文本 → 应在设备侧/环回收到。
2. **USB 热插拔**：运行中拔掉 USB 转串口 → 状态应转"串口重连中"→ 重新插入后自动恢复"运行中"。
3. **局域网跨机访问**：从另一台电脑连接 `<主机IP>:9001` 收发数据（本机已验证 TCP 监听与防火墙提示，跨机需第二台设备）。
4. **多客户端并发冲突**：多客户端模式下两台设备同时控制同一串口设备，确认应用层协议是否冲突（软件保证字节不交叉，不保证请求配对——设计如此）。
5. **长时间稳定性**：多映射连续运行 24h+，观察内存/句柄是否平稳（自动化测试验证了队列上限机制，未做长跑）。
6. **Windows 10 1809 全新系统安装**：本机为 Windows 11，未在干净 Win10 上实测；self-contained 发布理论上兼容。
7. **DPI 缩放**：在 125%/150% 缩放屏幕检查布局（WPF 矢量布局通常无碍，未实测）。

## 6. 开发过程中发现并修复的关键问题（备查）

1. **SerialPort.BaseStream.ReadAsync 超时陷阱**：APM 路径超时抛 `IOException(ERROR_OPERATION_ABORTED)` 而非 `TimeoutException`，导致真实串口 200ms 一次的错误重连。已改为同步 `Read`（线程池执行）+ `ReadTimeout`。
2. **Pipe AdvanceTo 死锁**：`examined` 标记到缓冲区末尾会令剩余数据永久卡死（写入端停止后 ReadAsync 不再唤醒）。consumed 与 examined 必须一致。
3. **Windows 端口冲突语义**：监听已占用端口（对端设 SO_REUSEADDR）时报 `AccessDenied` 而非 `AddressAlreadyInUse`，需两者都归类为"端口被占用"。
4. **WPF-UI SymbolRegular 命名**：4.3.0 采用 FluentUI 2.x 命名，`Add24/Play24/Settings24` 等基础名不存在（运行时才报错），需按程序集实际枚举取用。

## 7. Linux 客户端 Tab 补全问题排查记录（2026-10-11，已结案）

**现象**：Ubuntu 主机通过 TCP 客户端（nc / screen //telnet）访问海思板调试串口（COM7→9001），
输入 `ifc` + Tab 时补全不生效。

**排查过程**：
1. 修复了真实存在的"网络→串口并发写乱序"隐患（见第 6 节），问题未随之消失；
2. 分析 nc 的 stdin 为行缓冲（icanon）：Tab 被本地终端攒住，回车才发送——解释了
   "回车后补全生效"的 nc 现象；
3. 用户改用 screen 后 Tab 仍失灵，断开 screen 后用原始 TCP（Python socket，逐字符
   60ms 间隔发送 `ifc` + `	`）实测设备链路：

```
逐字符回显: b'ifc'
Tab 响应 HEX: 0d 7e 20 23 20 69 66 63 6f 6e 66 69 67 20 1b 5b 4a
           =   "~ # " "ifconfig" " " ESC[J
包含补全文本: True（1.5s 内立即响应）
```

**结论**：SerialBridge 与串口链路对 Tab 的透传完全正常（设备立即回发补全重绘）。
- nc 失灵根因 = 本地终端行缓冲，属使用方式问题；
- screen //telnet 失灵根因 = screen 的 telnet 协议栈与哑透传对端先天不匹配
  （发送 IAC 协商且按键未到达设备），screen 不适合直接连 SerialBridge；
- 推荐方案：socat PTY + picocom（方式一），或脚本化访问（skills/serial-tcp-uart）。
